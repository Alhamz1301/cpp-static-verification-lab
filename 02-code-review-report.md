# C++ Static Verification — Code Review Report

This report is based on a static inspection of the supplied `game.cpp` source code. Each finding identifies a distinct defect, explains the consequence, and recommends a concrete fix without changing the original program during the initial review.

| Line Number | Defect Type | Why It Is a Problem | Proposed Fix | Severity |
|---|---|---|---|---|
| 45-50 | Assignment used instead of comparison in `findMonster()` | The condition `if (monsters[i]->id = id)` assigns `id` to `monsters[i]->id` instead of comparing values. This causes every monster to match the first candidate, returning the wrong pointer and making the game logic invalid. | Use `if (monsters[i]->id == id)` and return the matching pointer only when the IDs match. | High |
| 40-43 | Missing capacity check in `spawnMonster()` | `monsters[monsterCount] = new Monster(...)` writes beyond the fixed array if `monsterCount >= MAX_MONSTERS`. This causes out-of-bounds writes and corrupts memory. | Add a guard such as `if (monsterCount >= MAX_MONSTERS) { /* report error */ return; }` before inserting a monster. | Critical |
| 112-119 | Excessive monster spawning in `main()` | The program creates six monsters even though `MAX_MONSTERS` is five. This exceeds the intended array capacity and can cause undefined behavior when the next spawn occurs. | Reduce the number of created monsters to at most five or add runtime validation to reject any excess spawn. | High |
| 53-59 | Null-pointer dereference in `attackMonster()` | `Monster* m = findMonster(id);` can return `nullptr`. The code then immediately accesses `m->health` and `m->health -= damage`, causing a crash if the monster is missing. | Validate `m` before dereferencing: `if (m == nullptr) return 0;` or throw/log an error. | Critical |
| 55-59 | Incorrect signed/unsigned comparison and negative-damage handling | `unsigned int dmg = damage;` converts negative damage to a large positive value. The condition `if (m->health - dmg < 0)` then compares a signed value to an unsigned conversion, which is wrong and can produce the wrong result or wrap-around. | Keep damage as a signed integer, validate non-negative input, or convert with explicit checks: `if (damage < 0) return 0;`. | High |
| 62-67 | Out-of-bounds array access in `totalMonsterHealth()` | The loop uses `i <= monsterCount`, which reads `monsters[monsterCount]` when `i` reaches the count. That element is outside the valid range and can read garbage data or crash. | Use `for (int i = 0; i < monsterCount; ++i)` so the loop stays within the valid element range. | Critical |
| 70-73 | Dangling reference returned by `getMonsterLabel()` | The function returns a reference to a local variable `label`, which is destroyed when the function exits. Any caller receives a dangling reference and use-after-destruction behavior is possible. | Return a `std::string` by value instead of `std::string&`, or construct and return a `std::string` object directly. | High |
| 76-80 | Uninitialized accumulator in `averageAttack()` | `double sum;` is declared without initialization. The loop adds to an indeterminate value, producing undefined behavior and unpredictable averages. | Initialize the accumulator: `double sum = 0.0;`. | High |
| 76-80 | Division by zero in `averageAttack()` | If `monsterCount == 0`, the function returns `sum / monsterCount`, which divides by zero. This can cause runtime failure or invalid numeric output. | Check `if (monsterCount == 0) return 0;` or handle the empty-state explicitly before dividing. | High |
| 83-86 | Use-after-free in `defeatMonster()` | `delete m;` frees the `Monster`, but the next line prints `m->name`, dereferencing memory after free. This is an immediate use-after-free defect. | Remove the object from the collection and only access it while still valid, or print the stored name before deletion. | Critical |
| 83-86 | Failure to remove defeated monsters from the collection | After deleting a monster, the `monsters` array still contains the same pointer, and `monsterCount` is not updated. The game later continues to treat a removed monster as alive, causing stale references and invalid iteration. | Erase the pointer from the array, shift remaining elements left, and decrement `monsterCount` after a delete. | High |
| 25-38 | Shallow copying and double-deletion risk in `Game` | `Game` owns raw pointers but defines no copy constructor or copy-assignment operator. The default copy copies the pointer addresses, so multiple `Game` objects own the same heap memory and both may delete the same object. | Implement a proper copy constructor, copy-assignment operator, and destructor, or store smart pointers (e.g., `std::unique_ptr<Monster>`) instead of raw pointers. | Critical |
| 133 | Shallow copy in `Game copy = game;` | The copy is performed without custom ownership rules. The second object shares the same monsters and can lead to double deletion when both destructors run. | Replace raw ownership with `std::unique_ptr` or implement deep-copy semantics explicitly. | Critical |
| 94-99 | Missing return value in `playerRank()` | If the score is 100 or less, nothing is returned. This leaves the function without a defined result and triggers undefined behavior at runtime. | Add a default return value, for example `return 3;` or another rule consistent with the game design, after the conditional checks. | High |
| 101-110 | Unsafe character-buffer input in `readBoss()` | `char* name = new char[10];` followed by `std::cin >> name;` is unsafe because user input can exceed the buffer length and overflow the array. This is a classic buffer-overrun bug. | Use `std::string name; std::cin >> name;` and avoid raw dynamic arrays. | Critical |
| 102, 109 | Incorrect `delete` versus `delete[]` | `new char[10]` is paired with `delete name;`, but the correct deallocation for arrays is `delete[] name;`. Using `delete` on an array is undefined behavior. | Replace the allocation with `std::string` or use `delete[] name;` if raw memory must be used. | High |
| 90-91 | Integer truncation in `calculateDamage()` | The function returns `attack * armorPercent / 100` using integer arithmetic before the result is converted to `double`. Fractional damage is discarded, and the calculation can be inaccurate for gameplay values. | Use floating-point arithmetic: `return static_cast<double>(attack) * armorPercent / 100.0;`. | Medium |
| 70-73 | Missing pointer validation in `getMonsterLabel()` | `Monster* m = findMonster(id);` is dereferenced immediately without checking whether `m` is null. If the monster does not exist, `m->id` and `m->name` crash the program. | Validate `m == nullptr` before using it and return a safe error string or value. | High |
| 27-33 | Uninitialized pointer-array elements | The `monsters` array is declared but not filled with `nullptr` in the constructor. Reading or deleting an uninitialized element is undefined behavior. | Initialize all elements: `std::fill(std::begin(monsters), std::end(monsters), nullptr);` or loop through the array. | High |
| 121 | Memory leak of `bonus` in `main()` | `Monster* bonus = new Monster(...)` allocates memory but no corresponding `delete` is performed before the program exits. This leaks memory and can worsen over time in repeated runs. | Use a smart pointer or delete the object when it is no longer needed. | Medium |
| 35-38 | Destructor uses stale ownership assumptions | The destructor deletes every element from `0` to `monsterCount - 1`, assuming all stored pointers are valid and uniquely owned. This is unsafe when pointers are stale, duplicated, or the count fails to reflect valid ownership. | Track ownership accurately, reset pointers to `nullptr`, and ensure the count and array remain consistent before destruction. | High |
